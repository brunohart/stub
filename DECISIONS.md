# Decisions

Architecture decision records for Stub. Newest at the bottom. A decision is a decision until a later ADR says otherwise.

## ADR-001 — The heuristic parser is the floor, the model is measured against it

**Date:** 2026-09-06 · **Status:** decided

Stub reads ticket stubs with two parsers: a regular-expression parser built from cinema-ticket folklore (`HeuristicParser`) and the on-device language model through Foundation Models guided generation (`ModelParser`). The heuristic runs everywhere, always. The model runs only when `SystemLanguageModel.default.availability` is `.available`, and if it fails or returns no title, the heuristic result is used. Both write `readBy` and `confidence` onto the stub, and the raw Vision text is kept verbatim so a human can overrule either.

**Why.** On Day 0, in the iOS 26.2 simulator on macOS 26.6.2, the model reported itself available and then failed every request with `ModelManagerServices.ModelManagerError 1026`. Without the floor, the app would have had nothing. With it, all four fixtures were filed correctly. An app whose headline feature is on-device AI has to be honest about when the AI is not there, and useful anyway.

**Consequences.** The heuristic gets tests; the model gets an eval table (Day 3) that compares it to the heuristic on the same fixtures. The UI names which one did the reading.

## ADR-002 — The look is specified in SwiftUI first; Metal is an implementation, not the identity

**Date:** 2026-09-06 · **Status:** decided, Metal switch-over planned Day 1

The silkscreen treatment (desaturate, contrast, multiply onto parchment, grain), the misregistered orange plate, and the paper grain are defined as view modifiers in `Design/Paper.swift` and `Design/Type.swift`. Day 0 implements them with SwiftUI blend modes plus a Core Image noise plate. The Metal shaders in `Shaders/Silkscreen.metal` compile into the bundle and take over on Day 1 behind a switch.

**Why.** Apple's Metal toolchain catalog fetch failed twice on Day 0 (`Failed fetching catalog for assetType com.apple.MobileAsset.MetalToolchain`) before succeeding on the third attempt. The visual identity cannot depend on a download. Specifying the look at the modifier boundary means the implementation can change without the callers noticing.

## ADR-003 — Simulator first, with a seed path that exercises the real pipeline

**Date:** 2026-09-06 · **Status:** decided

Every day's work must run in the iOS 26 simulator. Because the simulator has no camera and cannot be tapped from a script, Debug builds accept `-seed` (and `-reset`) launch arguments that push the bundled fixture stubs through Vision and the parsers and file them. `scripts/run.sh --seed --reset --shot …` is the daily proof.

**Why.** Bruno wants to iterate on design and interaction daily without a device in hand, and a scheduled build has no hands at all. Fixtures are synthetic tickets drawn by `scripts/make-fixtures.swift`, so they are honest inputs to OCR rather than hand-typed strings.

## ADR-004 — `project.yml` is the project; the `.xcodeproj` is a build artefact

**Date:** 2026-09-06 · **Status:** decided

The Xcode project is generated by XcodeGen from `project.yml` and is git-ignored. Targets, Info.plist keys, fonts and build settings are edited there.

**Why.** Diffs stay readable, merges stay possible, and an agent can add a widget target on Day 5 without touching a pbxproj by hand.

## ADR-005 — Private by construction

**Date:** 2026-09-06 · **Status:** decided

No network calls, no analytics, no account. Photos are stored in SwiftData with `.externalStorage`. Everything the reader saw is kept on the device and shown to the user on request.

**Why.** The product's one-line promise is "never uploaded". The architecture has to make that promise impossible to break by accident, not merely intended.

## ADR-006 — Two faces and a mono, numbers only in mono

**Date:** 2026-09-06 · **Status:** decided

Host Grotesk for words (Medium for display at −0.03em tracking), Newsreader for the single italic sentence and for reading, Fragment Mono for dates, seats, prices and confidence percentages. Hierarchy comes from size and space, not weight. The fonts ship as variable TTFs renamed without brackets (iOS did not register `HostGrotesk[wght].ttf` from `UIAppFonts`; `HostGrotesk-Variable.ttf` registers all six named instances). A Debug-only `FontAudit` logs what registered at launch.

**Why.** This is the designedbybruno type system, settled on 2026-09-03. The bracket finding cost twenty minutes and is recorded so it costs nothing next time.

## ADR-007 — Two detectors for the crop, and a quadrilateral that hugs the frame is not a ticket

**Date:** 2026-09-07 · **Status:** decided

`StubCrop` asks Vision's `DetectDocumentSegmentationRequest` first. If it finds nothing, or its quadrilateral touches three or more edges of the frame, `DetectRectanglesRequest` is asked next and its largest accepted rectangle wins. Both are straightened with `CIPerspectiveCorrection`. The full photograph is the floor, and `StubReader` falls back to it again if the crop reads as no text. The seed log and `StubReader.Result.detector` say which detector found the ticket.

**Why.** On the iOS 26 simulator on this Mac, segmentation returns the same full-width bottom-quarter strip for every fixture at 0.83–0.99 confidence, at every input scale, through both the new and the `VN` API. The same request on macOS finds the ticket to the pixel. This is the language-model failure again (ADR-001): a model that reports itself confident and is not there. The rectangle detector is arithmetic, not an asset; it found all four fixtures at 1.0, within a few pixels of the Mac's segmentation. Two detectors mean the crop works on the host the daily slot actually runs on, and the edge rule means a lying detector is caught by geometry rather than by luck.

**Consequences.** Do not remove the rectangle path when segmentation starts working on a device; keep both and let the log show which one is winning. Real photographs where the ticket fills the frame will fail the edge rule and fall to rectangles or the full frame, which is the ticket anyway.

## ADR-008 — Build products live outside `~/Documents`

**Date:** 2026-09-07 · **Status:** decided

`scripts/build.sh`, `test.sh` and `run.sh` use `~/Library/Developer/Xcode/DerivedData/Stub-scripts` as derived data (override with `STUB_DERIVED_DATA`). `build/` keeps only logs, test results and the slot markers.

**Why.** `~/Documents` on this Mac is an iCloud file-provider domain. The provider stamps every `.app` package under it with `com.apple.FinderInfo` and `com.apple.fileprovider.fpfs#P`, and `codesign` then refuses the bundle: "resource fork, Finder information, or similar detritus not allowed". Stripping with `xattr -cr` before signing lost the race every time, and a `.nosync` folder was tagged too. Day 1 started with the floor down for this reason.

**Consequences.** The repo can stay where Bruno keeps it. Anything that must be signed is built elsewhere. If the repo ever moves out of a file-provider domain, this can be reverted, but there is no reason to.

## ADR-009 — Two uneven columns stay; the table is the width of the screen

**Date:** 2026-09-08 · **Status:** decided

The table keeps its two columns at 1.15 : 0.85, overlapping by six points, the right column starting lower (DESIGN.md rule 4). The content stack inside the `ScrollView` carries `frame(maxWidth: .infinity, alignment: .leading)` so the columns are sized against the screen, not against the widest line of text above them.

**Why.** Day 1 asked whether landscape stubs at 2.3:1 want one wider column. The plates were small because the whole table was small: the `VStack` in the `ScrollView` took the width of its widest non-greedy child, the one-line season sentence, and `containerRelativeFrame` resolved against that. With the width restored the plates read at about 185pt and 137pt, the cinema names fit, and the zoom transition has a source worth growing from. A single column would trade the corkboard for a list.

**Consequences.** Anything laid out inside the table's scroll content must not depend on the sentence's length. The Debug `-drive` argument (`DebugDrive`) is the second honest stand-in for hands in the simulator after `-seed` (ADR-003); interaction days should extend it rather than add a third mechanism.

## ADR-010 — The model reads with the heuristic's draft in hand, and is scored in the drawer's shapes

**Date:** 2026-09-09 · **Status:** decided

`StubReader` runs `HeuristicParser` first, always, and passes its draft to `ModelParser` as a hint in the prompt ("a first pass by a rule-based reader: keep what the text confirms, correct what it does not, fill what it missed"). The model's answer streams (`streamResponse(to:generating:)`) and each snapshot is normalised through the same functions the heuristic uses (`normalisedScreen`, `normalisedSeat`, `stripFormats`, comma prices) before it reaches the fields or the eval table. Dates from the model are read as wall-clock time: any zone designator is dropped (`wallClock`). The eval harness (`StubTests/EvalTests.swift` → `docs/evals.md`) scores the heuristic, the cold model and the hinted model on the same eight fixtures, and asserts only the floor: the heuristic reads seven of eight titles and seats.

**Why.** Day 3 was the first day the model answered. Cold, on eight fixtures, it read 2/8 prices (it guesses USD for `$`), 7/8 dates (it swapped day and month once), 6/8 cinemas (it shortens "Event Cinemas Queen St" to "Queen St" and spelt "Roxxy"), and before normalisation it lost screens and seats it had read correctly by leaving them as printed ("SCR 2", "SEAT D 4"). Its first dates were all twelve or thirteen hours late because it wrote ISO 8601 with a `Z` for a ticket that prints the time on the wall of the cinema. With the heuristic's draft as a hint it read 8/8 on every field, at the same latency as cold (median 8.7 s against 8.9 s); the run before had it at 7/8 titles ("Aftrsun"), so it is not the same reader twice. The hint costs nothing and the correction is real, so the hinted model is the production path when the model is there. The heuristic is still the floor (ADR-001): it reads 8/8 on all six fields in about a millisecond.

**Consequences.** Never compare the model to the heuristic on raw strings; compare on what the drawer would file. Any new normalisation belongs in `ModelParser.draft(title:…)` so both columns of the table get it. A field the model reads better than the regex has to show up in `docs/evals.md` before the regex is loosened for it. The eval test takes about two minutes when the model is present and is the reason `scripts/test.sh` prints nothing for stretches; that is expected, not a hang.

## ADR-011 — The season is counted by hand and only phrased by the model

**Date:** 2026-09-10 · **Status:** decided

`SeasonSummary` counts the drawer (films, distinct cinemas, most visited, busiest month and weekday, total paid by currency) in a millisecond and writes `handSentence`. The on-device model is given only the summary's `brief` (one fact per line) and asked, through `@Generable struct Season`, for one sentence. Whatever it writes is judged by `SeasonRules` (under twenty words, no exclamation mark, no emoji, no digit, one sentence) and refused if it breaks one; the hand sentence stands until an accepted sentence arrives, and stands for good if none does. The sentence is cached against `SeasonSummary.key`, an FNV-1a hash of the brief, so the model is asked once per drawer, not once per launch, and the sheet's numbers are never the model's.

**Why.** The sentence is the one place the app is allowed a voice, and a language model is the right tool for a voice. It is the wrong tool for arithmetic and for restraint: the rules that make the line read as this app's ("dry, under twenty words, numbers spelled out") are the rules a model is most likely to break with enthusiasm. Instructions are a hope; a check on the way out is a rule. The hash is FNV over the brief rather than `Hashable` because Swift's hasher is seeded per process and a cache that forgets on relaunch is not a cache.

**Consequences.** New facts for the sentence go into `SeasonSummary` and its brief; they change the key and the sentence regenerates. `SeasonModel.update` waits for `StubReader.isBusy` to clear before asking, so a seed of eight stubs produces one sentence at the end and an import never queues behind it. Any new rule for the sentence is added to `SeasonRules.judge` and to the test, not only to the instructions.
